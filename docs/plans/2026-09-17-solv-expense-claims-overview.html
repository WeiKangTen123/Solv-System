Solv Expense Claims: system plan from receipt to report

Prepared 17 Sep 2026 For Wei Kang, Solv Reuse source: xero-invoice-app-master at master 99ba5ef Samples: 2 Marriott folios (INR), 2 report templates
The answer

Build Solv as a new, standalone app on the same stack as the Xero automation (Node 22, Express, SQLite, React + Vite, Gemini as the receipt reader) and port about twenty of its proven modules with their tests: the AI receipt reader, two-tier duplicate detection, the crash-safe job queue, phone QR capture, ZIP + claim-form import, client-side photo compression, authentication and the deploy/backup tooling.

Solv then adds the five things the Xero app does not have: reading scanned PDFs (both of your samples are scans with no text layer, and the Xero app stores those without reading them), exchange-rate conversion with the rate, its date, its source and the fetch time frozen on every line, an Expense Report entity with a cover, a PDF/XLSX export in your template's structure with the receipts appended, and an employee → manager → finance approval flow.

What first: scaffold the repo and prove the reader on your two Marriott folios before touching exchange rates or the report. Extraction is the only uncertain component; everything downstream of it is deterministic. Eight decisions are listed at the end; my recommendation is marked on each.

What the samples say

The receipts

Both files in samples/receipts/ are Indian hotel tax invoices for the same traveller, Ms Elaine Xin Yu Khoo of Singapore. They are harder than the Singapore receipts the Xero app was tuned on, in five ways that shape the design.

  1. They are scans. Extracting text with the Xero app's own parser returns zero characters for both. The Xero app's rule for that case is "stored but not read; type the fields by hand". Solv must render the pages to images and read them with the vision model.
  2. They are multi-page single documents. The Xero app splits a PDF page by page into separate claims, which is right for a stack of taxi receipts and wrong for a four-page folio. Solv needs a document-level read: all pages of one invoice number in one model call.
  3. One receipt spans several report columns. A folio is Lodging and Meals at once. The report template has category columns, so one receipt must be able to split into several lines that still add up to the receipt total.
  4. They carry a colleague's charges. Both hotels moved a second guest's room onto Elaine's bill. The claim needs a "paid on behalf of" flag per line so finance can see who really incurred it.
  5. They are in INR with Indian GST. The tax is recorded, but it is foreign tax: it stays inside the claimed amount and is not Singapore input tax. The report says so.

The report structure

The two images in docs/reference/report-templates/ are two templates that answer different questions. The first (Business Trip Expense Report) has a trip cover: employee, department, purpose, trip dates, days of stay, destination, total. Its table has four category columns. The second (Expense Report) has a pay-period cover with statement number, employee ID and manager, eight category columns, a subtotal, an advances line and a total reimbursement, an itemised "Other" box, and an office-use area. Solv's report takes the union: the trip cover from the first, the column set, advances and office-use block from the second, and adds what neither has because neither is multi-currency: original currency, rate, base amount, and a rate footnote. The category columns are configurable per company, so the default can be either template's set.

Architecture options

Recommended

B. New Solv app, same stack, ported modules

A fresh repository with the Xero app's layout (main/, ui/, co-located tests). Modules are copied file by file, each with its test, and the tests must pass before Solv-specific code is written.

  • Clean company / employee / report model built for approvals
  • Ported tests keep protecting ported code
  • Xero posting later through the same ported xero/ modules
  • Cost: one to two days of scaffolding; some duplication with the Xero app until a shared package is worth it
Alternative

A. Extend the Xero app in place

Add reports, FX and approvals to the existing app.

  • Fastest first demo; nothing to port
  • But its model is "each user connects their own Xero org", with strict per-user isolation, and claims share the invoices table with bills
  • Company-wide approvals fight that isolation; two products end up in one repo and one deploy
Alternative

C. Monorepo with a shared package

Extract the reader, dedup, queue and stores into a package both apps depend on.

  • Best long-term shape
  • Premature now: worth doing the second time both apps change the same module

System shape

Deployment is the same as today: one VM, pm2, nginx, SQLite on the same disk, a verified daily backup, a deploy script that waits for CI. Solv runs as a second pm2 process on that VM or on its own; the runbook transfers unchanged.

Data model

SQLite, WAL mode, foreign keys on, cents stored as integers, timestamps in UTC and formatted in the company timezone. Every table hangs off companies so a second company can be added later without a migration.

Pipeline: one receipt's journey

  1. Arrive. Desktop drag-drop, phone camera through a QR pairing token, or a ZIP plus claim-form XLSX. Photos are resized and re-encoded in the browser; PDFs pass through untouched.
  2. Store before anything else. The file is hashed (SHA-256) and written to disk; a receipt row and an expense row in status reading are created. An exact hash match is a certain duplicate: the expense is marked duplicate pointing at the original and no second file is written.
  3. Classify and read. An image goes to the vision reader. A PDF with a text layer goes to the text reader, with pages that share an invoice number merged first. A PDF with no text layer is rendered page by page and all pages go to the vision reader in one call as one document. Photos holding several receipts are split using the existing bounding-box guard.
  4. Normalise. Merchant, date, time, currency, total, tax, subtotal, invoice number, line items each with a category, confidence. Unlisted categories are dropped, tax above total is rejected, negatives are treated as unread. Everything is the Xero app's normaliser plus the per-line category.
  5. Suspect duplicates. Same merchant, same date, same amount as an existing expense raises a warning for a person to settle; it never auto-marks.
  6. Convert. The FX service looks up the rate for (currency → base, policy date), serving from fx_rates or fetching and caching it, and freezes rate, rate date, source and fetch time on every line. If no provider answers, the line is marked rate pending and the report cannot be exported until finance supplies one.
  7. Split into lines. Line items are grouped by category into report lines (a folio becomes Lodging and Meals). The claimant can edit the split; the lines must total the receipt.
  8. File. The expense is offered to the open draft report whose dates cover the receipt date, or stays "unfiled" on the home screen until the claimant files it.
  9. Review. The claimant checks the fields against the image, types the business purpose (the reader never invents one), marks lines paid on behalf of a colleague, and marks the expense reviewed.
  10. Submit, approve, pay. Submitting locks the report. The manager approves or rejects lines with a reason. Finance exports, marks paid, and, in phase 5, posts to Xero.

Failure rules, carried over from the Xero app and kept: the file is stored before any parse; a parse failure yields a saved expense with blank fields, never a lost receipt; a model outage degrades to manual entry; every job survives a restart and is retried up to three times before it is set aside with its error visible.

Exchange rates

The report has to say what rate was used, for which date, from where, and when it was fetched. That is only possible if the rate is written down at the moment it is applied and never recomputed. Everything below follows from that.

Direction and arithmetic

A rate is the number of base-currency units per one unit of the foreign currency (SGD per INR). Each line is converted and rounded to the cent on its own; the report total is the sum of the lines. Your samples show why the rule has to be printed: the Mumbai folio converts to 594.18 as one figure but its two lines round to 556.21 and 37.98, which sum to 594.19. Neither is wrong; the report states which rule it follows.

Policy, a company setting

  • Rate on the receipt date (default and recommended): the accounting convention, and what IRAS expects for a foreign-currency expense.
  • Rate on the submission date: simpler for the claimant, less defensible in an audit.
  • Monthly fixed table: finance uploads one rate per currency per month; the report cites the table.

Historical rows are cached forever. The "latest" row is refreshed hourly while the app is used. Provider calls time out at five seconds and run inside the job runner, so a slow provider never blocks an upload.

What the report prints, per foreign line: INR 43,131.36 × 0.01341 = SGD 578.39. And once per (currency, rate date) in the footnote: "INR→SGD 0.01341, European Central Bank reference rate for 4 Sep 2026, via Frankfurter, fetched 17 Sep 2026 15:31 SGT. Policy: rate on the receipt date. Each line is converted and rounded to the cent; the total is the sum of the lines."

When a report is posted to Xero, the bill carries the same rate in CurrencyRate, so Xero's base-currency figure matches the printed one instead of Xero applying its own rate of the day.

Security, operations, tests

Security

  • Kept from the Xero app: JWT with role read from the database on every request, bcrypt passwords, AES-256-GCM for stored secrets, helmet, per-user rate limits, signed short-lived image and export tokens, single-use QR tokens that grant upload only, path sanitisation, per-user file directories.
  • Added: route-level role checks (an employee sees only their own expenses; a manager sees their direct reports' submitted reports; finance sees the company), an audit table written on every status change and rate override, and report locking after submission.

Operations

  • pm2 with restart backoff, nginx in front, daily verified SQLite backup, npm run backup:pull to copy the set off the box, deploy that waits for green CI and proves the running commit. All ported.
  • New: a nightly job that refreshes "latest" rates and reports any line still pending a rate; storage growth is watched because originals are now full size.

Tests

  • Jest and supertest, tests co-located, data and logs in a temp directory under test. Ported modules bring their tests; the port is not done until they pass in the new repo.
  • New tests: the page renderer (page count, size, a text-free PDF yields images), the multi-page single-document read against both Marriott folios with mocked model replies, the FX service (cache hit, provider fallback order, weekend resolution, manual override, rate pending), the line split reconciliation, the report document definition (rows, columns, category totals, the footnote content, rounding rule) without rendering, the approval state machine, and role guards on every route.

Phases and what first

What first

Phase 0 and Phase 1, in that order, with your two Marriott folios as the acceptance test. The reader is the only part of this system whose result is uncertain: a four-page scanned Indian GST folio with a colleague's room on it is a harder document than anything the Xero app has read. Exchange rates and the report are deterministic and can be built with confidence once the extracted fields are trustworthy. The acceptance test for Phase 1 is concrete: upload each folio and get one expense (not four), the right merchant, dates, currency, total and tax, lines split into Lodging and Meals that sum to the total, and the transferred room detected as paid on behalf of a colleague.

New repository with the Xero app's layout. Port auth, users, crypto, logger, database and migrations, backup, job runner, receipt store, thumbnailer, Gemini client, the UI shell and API client, CI and deploy. Add companies, roles, and the new tables. Every ported test passes.

Decisions needed from you

Answer by number. Where you have no preference, I take the recommendation.

  1. Standalone Solv app, or extend the Xero app?
    Recommended: standalone, same stack, ported modules. Extending is faster for a demo and slower for everything after it.
  2. Company name and base currency on the report?
    Assumed: Solv, SGD, Asia/Singapore. Say if the claiming entity is a different company or if any staff claim in a different base.
  3. Exchange-rate policy by default?
    Recommended: rate on the receipt date from ECB reference rates, with a manual override for finance. Alternatives: submission-date rate, or a monthly fixed table.
  4. Report columns?
    Recommended: configurable per company, defaulting to Air & Transport, Lodging, Meals, Entertainment, Phone, Fuel/Mileage, Other (the second template), collapsed to used columns on paper. Or keep the four-column trip layout.
  5. One receipt to many lines, or one line per receipt?
    Recommended: many lines, split by category, reconciled to the receipt total. A hotel folio is the case for it.
  6. Approval chain?
    Recommended: one manager, then finance marks paid. Two-level approval can be added later as a company setting.
  7. Xero posting granularity, when it comes?
    Recommended: one bill per report, with a line per expense line and the receipts attached. One bill per line is possible if finance prefers to match receipts one to one.
  8. Keep Gemini as the reader?
    Recommended: yes for now; the keys, rotation and rate limiting are already built. The reader is one function, so a different model is a one-file change if the folio accuracy test disappoints.

Assumptions I made

  • "Cover" means both the system's home screen and the cover page of every printed report; I built the plan for both.
  • Employees, managers and finance are staff of one company; the design keeps a company table so a second one is a data change, not a migration.
  • The Xero app keeps running as it is; nothing in this plan changes it.
  • Originals are stored at full size; the 3 MB limit applies only to the copy attached to a Xero bill.
  • The claim-form XLSX that staff email today (date, description, currency, amount, exchange rate, SGD amount, category columns) stays supported through the batch import; Solv's own screens make it optional.
